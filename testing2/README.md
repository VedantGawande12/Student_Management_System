# Aurora fresh campus dataset — v2

A newly constructed synthetic campus for testing your CIT-format importer,
scheduler, AI request parser and rescheduling approvals. Records are generated
from scratch; this is not the previous dataset with names replaced.

New institute, department names, entity IDs, people, building/room names,
capacity distribution, cohort sizes, course catalogue, faculty assignments,
session/group links, fixed slots, elective memberships, preferences,
unavailability, maintenance, bookings, dates, descriptions and disruption.
There is deliberately no one-to-one mapping to the earlier records.

## What “change every value” means here

All campus records and relationships were rebuilt. Format vocabulary and
scheduling rules remain compatible: field names, MON–FRI/SAT, period IDs,
AM/PM, role names, room-type codes, category codes, lab starts P2/P6,
lunch after P5, clock definitions and the priority policy retain their specified
meaning. Booleans/nulls and legal durations necessarily recur. Changing every
literal value would break the CIT format and hard constraints. Dates and
requested slots are fresh; the official clock model is retained.

## Files and workflow

1. Import `cit_fresh_v2.json` with your app's dataset loader.
2. Generate your own schedule; the included `reference.schedule.json` is a
   comparison fixture generated by `generate.py`, not your application's output.
3. Apply `sample_disruption_v2.json`. It exercises all five change types and
   intentionally blocks an occupied baseline slot. Repair feasibility has not
   been established; your app should propose a validated repair or explain why
   none exists, then require independent Admin approval before applying.
4. Exercise `sample_requests_v2.md` through an editable preview before submission.
5. Inspect `verification.json` for checks performed.

These are JSON imports, not SQL. Supabase SQL Editor cannot load them directly;
your backend importer must map them into your tables. Original files are untouched.

## Booking probes

- AV-B226: attendance 1,403 exceeds all room capacities. Must not approve.
- AV-B227: club claims institute-event priority. Effective category stays club_event.
- AV-B228: cancelled. Must not approve.
- AV-B229: nonexistent preferred venue AV-PHANTOM; don't create it. Valid alternatives
  are permitted if the app explains them and respects actual room constraints.
- AV-B230: three-hour event in a two-hour window; cannot approve inside the window.
- AV-B231 / AV-B232: equal-category competition for AV-F31 Friday P10–P11;
  earlier submission must have priority, subject to other higher-priority bookings.
- AV-B205 and AV-B217 are also cancelled.

Reference booking allocation is intentionally simple: exact-window allocation,
role caps, priority and timestamp ordering, no class displacement, no out-of-window
alternatives. It is not claimed to maximise the booking score.

## Reproduce and verify

Python 3.10+; standard library only:

```bash
python generate.py --output regenerated
python verify.py regenerated
```

Default seed is 270311. Identical seed produces identical fixture content.
The generator builds candidate teaching placements, simultaneous elective
baskets, multi-room exams with half capacity, and booking decisions. An independent
checker then evaluates those outputs; inspect its source for the supported checks.
The verification also checks foreign references and disruption sequence consistency.

The organiser's validator was not provided and was not run. Soft penalty optimality,
booking optimality and minimal-move repair are not asserted. The reference output
is for testing only: official submissions must be generated by your application
against the official dataset. Do not copy this reference as a competition export.
